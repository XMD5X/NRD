# Админ-панель поддержки СИБУР — MVP

Веб-приложение для сотрудников ИТ-поддержки и бизнес-заказчиков: запуск реальных
скриптов поддержки (PowerShell/Python) через веб-интерфейс, общая история всех
выполнений с возможностью скачать результат, загрузка сертификатов/счетов/полномочий,
аудит действий. Стенд развёрнут и работает через Docker Compose на этой машине.

Подробности — см. `docs/REFINED_VISION.md` (бизнес-видение) и `docs/HLD.md`
(архитектура; раздел 0 — актуальный статус реализации).

## Состав репозитория

```
backend/     Java 21 + Spring Boot API (+ адаптированные PS1/Python-скрипты поддержки
             в backend/src/main/resources/sample-scripts/)
frontend/    React (Vite) SPA; frontend/dist-prebuilt — уже собранная статика
             (см. раздел "Особенность сборки frontend" ниже)
nginx/       конфигурация реверс-прокси для докер-сборки
docs/        документация по системе (см. ниже)
docker-compose.yml   запуск всего стенда одной командой
deploy.bat / stop.bat   запуск/остановка стенда на этой машине (Windows)
build_and_export.bat    сборка + экспорт Docker-образов в dist_export/ для переноса
                        на другой ПК без интернета/Maven/npm (см. README-DEPLOY-OFFLINE.md)
```

## Быстрый запуск на этой машине (Windows)

1. Убедиться, что **Docker Desktop запущен** (иконка кита в трее). Если не запущен —
   открыть Docker Desktop вручную и подождать, пока он полностью поднимется
   (обычно 30–60 секунд), иначе `deploy.bat` упадёт с ошибкой подключения к
   `dockerDesktopLinuxEngine`.
2. Запустить `deploy.bat` (двойной клик или из командной строки). Он выполняет
   `docker compose up --build -d` и печатает адрес панели по завершении.
3. Открыть **http://localhost:18080** (backend напрямую для отладки — **http://localhost:18081**).
   Также доступен HTTPS: **https://localhost** (см. раздел "HTTPS" ниже).

Первая сборка занимает несколько минут (скачивание базовых образов, Maven-зависимостей).
Повторные запуски `deploy.bat` после изменений в `backend/` — быстрее (слои Docker
кешируются); после изменений в `frontend/` — см. раздел ниже, сборку frontend
нужно сделать отдельно **до** `deploy.bat`.

Порты 18080/18081 выбраны потому, что стандартные 8080/8081/5432 могут быть заняты
другими программами — при необходимости их можно поменять в `docker-compose.yml`.
HTTPS (443) — на стандартном порту (нужен для доступа как https://адрес-сервера без
указания порта); если 443 на хосте уже занят другой программой, поменяйте маппинг
"443:443" на, например, "18443:443" в `docker-compose.yml`.

Остановить стенд: `stop.bat` (или `docker compose down`).

## HTTPS

Панель доступна по HTTPS на **https://localhost** сразу "из коробки", без
дополнительной настройки. При первом запуске контейнер `web` автоматически
генерирует самоподписанный TLS-сертификат (см. `nginx/generate-cert.sh`) и
сохраняет его в именованном Docker-томе `nginx_certs` — при пересборках
(`docker compose up --build`) сертификат не перегенерируется, а переживает
пересборку вместе с томом; полностью новый сертификат появится только после
`docker compose down -v` (удаляет все тома, включая БД!) либо после ручного
удаления конкретно тома `nginx_certs`.

Так как сертификат самоподписанный, браузер при первом заходе на
`https://localhost` покажет предупреждение о недоверенном сертификате —
это ожидаемо для локального стенда, нужно подтвердить переход ("Дополнительно" →
"Перейти на localhost (небезопасно)" в Chrome, аналогично в других браузерах).
HTTP (`http://localhost:18080`) при этом продолжает работать как раньше —
принудительного редиректа на HTTPS нет.

Чтобы использовать вместо самоподписанного сертификата настоящий (от корпоративного
CA), нужно положить свои файлы `server.crt` и `server.key` в volume `nginx_certs`
(например, скопировать их в контейнер через `docker cp` в `/etc/nginx/certs/` и
перезапустить `web`, либо смонтировать volume как папку на хосте) — тогда
`generate-cert.sh` увидит, что сертификат уже есть, и не станет его перезаписывать.

Демо-учётные записи (создаются автоматически при первом запуске, см. `DataSeeder.java`):

| Логин | Пароль | Роль |
|---|---|---|
| `admin` | `admin12345` | Администратор |
| `business` | `business12345` | Бизнес-пользователь |

Демо-пароли слабые и известны всем, кто читал этот README — если панель выходит за
пределы вашей локальной машины (тестовый стенд, доступный коллегам), смените их
сразу после первого входа (учётки → сменить пароль/пересоздать пользователя).

## Безопасность

Проведён аудит и закрыт ряд уязвимостей (см. историю коммитов, "аудит безопасности"):

- **Загрузка скриптов была доступна не только администратору.** Из-за неверного
  правила в `SecurityConfig` любой авторизованный пользователь (включая demo-аккаунт
  `business`) мог загрузить свой PowerShell/Python-скрипт и выполнить его на сервере.
  Исправлено — загрузка скрипта (`POST /api/scripts`) теперь строго ADMIN-only.
- **JWT-секрет и пароль БД были захардкожены в `docker-compose.yml` и коммитились в
  git.** Теперь берутся из `.env` (в git не попадает, см. `.env.example`) —
  `deploy.bat` генерирует случайный `APP_JWT_SECRET` автоматически при первом запуске.
- **Path traversal при загрузке файлов** (скрипты, файлы бизнес-пользователей) —
  имя файла от клиента теперь очищается (`util/SafeFileNames`), не может увести
  запись за пределы целевой папки.
- Добавлена **защита от подбора пароля**: блокировка на 15 минут после 5 неудачных
  попыток входа (backend, `AuthService`) + rate limit на nginx (`/api/auth/login`).
  Заблокированный/уволенный пользователь теперь теряет доступ мгновенно, а не только
  после истечения уже выданного JWT (проверка блокировки на каждый запрос).
- Убрана утечка **различия "заблокирован" / "неверный пароль"** в ответе на логин
  (user enumeration).
- CORS: origin разрешён по маске `*` (`allowedOriginPatterns`), но
  `allowCredentials` выключен — авторизация идёт Bearer-токеном в заголовке
  `Authorization`, а не cookie, поэтому credentialed-запросы браузеру не нужны
  и опасная комбинация "`*` + credentials=true", найденная при аудите, не
  воспроизводится. (Промежуточный вариант с белым списком origin ломал вход
  из браузера в реальном окружении — curl без заголовка `Origin` проходил, а
  браузер с `Origin: http://<реальный-хост>` получал 403 от Spring Security
  ещё до контроллера — поэтому от привязки к конкретным хостам отказались.)
- nginx теперь отдаёт security-заголовки (CSP, X-Frame-Options, X-Content-Type-Options,
  HSTS на https, `server_tokens off`).
- backend-контейнер больше не работает от root (см. `backend/docker-entrypoint.sh`),
  а порт для отладки (18081) слушает только `127.0.0.1`, а не все интерфейсы.
- Общий обработчик ошибок больше не отдаёт клиенту текст непредвиденных исключений
  (могли утекать внутренние детали) — полный текст теперь только в логе сервера.
- Минимальная длина пароля при создании пользователя — 8 символов (валидация
  раньше была объявлена, но не применялась — `@Valid` отсутствовал в контроллере).

**Не сделано в рамках этого прохода (осознанно, чтобы не сломать уже развёрнутый
стенд без вашего решения)** — при желании доработать, дайте знать:
- Пароль Postgres по умолчанию (`adminpanel`) не менялся автоматически — Postgres
  применяет `POSTGRES_PASSWORD` только при первой инициализации пустого тома, слепая
  смена сломала бы подключение backend к уже работающей БД. Как сменить безопасно —
  см. `.env.example`.
- Версия Spring Boot (3.3.2) не обновлялась — обновление вслепую, без возможности
  собрать и прогнать проект в этой среде, рискованно; рекомендуется обновить и
  прогнать `docker compose up --build` самостоятельно при следующем удобном случае.
- JSON-тела в PowerShell-скриптах (`$userId`/`$account`, интерполяция в строку)
  не экранируют кавычки — не уязвимость (это не выполняемый код, а статический
  JSON-файл), но при вводе символа `"` в поле User ID итоговый JSON может получиться
  некорректным. Затрагивает ~40 файлов скриптов, не стал трогать без вашего ОК.

## Мониторинг и логи (раздел «Настройки», только ADMIN)

- **Системные ресурсы** — CPU/RAM/диск самого backend-процесса (JVM,
  cgroup-aware — внутри контейнера показывает лимит контейнера, а не хоста),
  размер БД PostgreSQL, разбивка места по каталогам данных backend (скрипты,
  результаты, загрузки, логи) и отдельно — сколько весит собранная статика
  фронтенда (эту цифру считает сам nginx при старте контейнера, см.
  `nginx/generate-metrics.sh`). Нагрузка (CPU/RAM) самого nginx-контейнера
  сюда намеренно не включена: получить её без Docker API (docker.sock)
  нельзя, а пробрасывать socket в backend ради одной цифры означало бы дать
  backend'у фактически root-доступ к хосту — после недавнего аудита
  безопасности такой компромисс сочли неоправданным.
- **Онлайн-статус пользователей** (страница «Пользователи») — зелёная точка
  у логина, если backend видел от него запрос за последние 5 минут (см.
  `OnlineUsersTracker`). Только в памяти процесса, не в БД — это индикатор
  "кто сейчас за компьютером", а не журнал посещений; список пользователей
  на фронтенде переопрашивается каждые 20 секунд, пока страница открыта.
- **Выгрузка логов** — четыре кнопки: логи backend (zip, ротация раз в сутки/по
  размеру — см. `logback-spring.xml`), логи фронтенда (zip, активные +
  архив), access-логи nginx (zip, по одному файлу на день — см.
  `nginx/nginx.conf`, том `nginx_logs` смонтирован в backend только на
  чтение) и журнал безопасности в формате CEF (Common Event Format,
  ArcSight) — попытки входа и действия пользователей (создание/блокировка
  учёток, загрузка и активация скриптов и т.п.) одним файлом, с читаемой
  датой/временем в каждой строке (`rt=...`), для передачи во внешний SIEM.
  У access-логов nginx пока нет автоматической чистки старых файлов (в
  отличие от backend/frontend) — они копятся без ограничения, при
  необходимости можно добавить отдельно.

## Редактирование скриптов онлайн (/admin/scripts, только ADMIN)

Кнопка «Редактировать» у каждого скрипта открывает его содержимое прямо в
браузере (обычный `<textarea>`, без подсветки синтаксиса) и позволяет сохранить
изменения — правится СРАЗУ файл на диске (не копия, не черновик), следующий
запуск задачи использует уже новую версию. Ограничение размера — 5 МБ (см.
`ScriptService.MAX_CONTENT_BYTES`). Полноценной истории версий нет: при
сохранении рядом с файлом остаётся ОДНА предыдущая версия (`<файл>.bak`,
перезаписывается на каждое следующее редактирование) — не история, а
возможность вручную откатить последний шаг, если срочно понадобилось.
Каждое сохранение пишется в историю действий (`SCRIPT_EDIT`, видно в истории
пользователя на странице «Пользователи» и в выгрузке CEF).

## Доступные задачи (реальные скрипты поддержки)

На главной странице задачи сгруппированы по плашкам (карточкам):

- **«Выдача прав доступа на счета для эталонных ролей»** — общая карточка с
  деревом "эталонная роль → банк" для категорий: ГРО (Платежи в рублях), ГУП
  (Платежи без импорта, этап 2), Права просмотра на все счета, Валютный контроль
  (Рубли), Валютный контроль (Валюта), SAP-PI. Каждая категория — 7 банков
  (АЛЬФА, ВТБ, ГПБ, РАЙФ/РАЙФ отсутствует у "Просмотра", РСХБ/РОССЕЛЬХОЗ, СБЕР,
  ЮКБ, КЕБ). Параметры: `userId` + номера счетов через запятую — на каждый счёт
  генерируется отдельный файл результата.
- **«Генерация ЭЦП»** — отдельная плашка (не входит в дерево выше). Скрипт
  `generation_ECP_RaiffeisenBankApi.py` регистрирует сертификаты ЭЦП для модуля
  RaiffeisenBankApi: три параметра через запятую (комментарии / номера
  сертификатов / даты истечения ДД.ММ.ГГГГ), на каждую ЭЦП — отдельный JSON.

Любая новая категория, которую заведут в `DataSeeder` и которой нет в списке
`ACCESS_RIGHTS_CATEGORIES` (`frontend/src/pages/DashboardPage.jsx`), автоматически
получит свою отдельную плашку — фронтенд для этого менять не нужно.

При запуске с несколькими значениями через запятую генерируется столько файлов,
сколько значений введено; если файлов больше одного, скачивание отдаёт zip-архив
(см. `ExecutionService.zipResultFiles`). Страница **«История»** показывает все
выполнения всех пользователей (кто, когда, что сгенерировал) с той же логикой
скачивания — это общий инструмент поддержки, а не приватный список.

## Особенность сборки frontend на этой машине

Сборка frontend (`vite build`) **внутри Docker на этой машине не работает** —
стабильно падает на `SyntaxError: Named export 'build' not found` при импорте
esbuild из vite (похоже на локальную особенность окружения — антивирус/сеть —
не баг проекта; воспроизводилось на трёх разных Node-образах). Поэтому:

- `frontend/Dockerfile` — однослойный, просто раздаёт через nginx уже готовую
  статику из `frontend/dist-prebuilt/`, без Node/npm/vite внутри Docker-сборки.
- **После любого изменения в `frontend/src/`** нужно вручную пересобрать и
  обновить `dist-prebuilt/` ПЕРЕД запуском `deploy.bat`:
  ```
  cd frontend
  npm ci
  npm run build
  # скопировать содержимое frontend/dist/ поверх frontend/dist-prebuilt/
  ```
  (Если сборка на этой машине тоже упадёт с той же ошибкой esbuild — собрать
  на любой другой машине/окружении и перенести только `dist-prebuilt/`.)
- Backend, наоборот, собирается **внутри** Docker через Maven без проблем —
  для него ничего вручную готовить не нужно, `deploy.bat` сам всё соберёт.

## Запуск без Docker (локальная разработка)

**Backend** (нужны JDK 21 и Maven, БД PostgreSQL 16 — либо локально, либо через
`docker compose up postgres`):

```bash
cd backend
mvn spring-boot:run
```

По умолчанию backend подключается к `jdbc:postgresql://localhost:5432/adminpanel`
(логин/пароль `adminpanel`/`adminpanel`) — см. `src/main/resources/application.yml`,
переменные окружения `SPRING_DATASOURCE_*`.

**Frontend** (нужен Node.js 20+):

```bash
cd frontend
npm install
npm run dev
```

Dev-сервер поднимется на `http://localhost:5173` и проксирует `/api` на backend
(`http://localhost:8080`, см. `vite.config.js`).

## Перенос на другой ПК

- **С исходниками** — собрать zip всего репозитория (кроме `frontend/node_modules`
  и `dist_export/`), на целевом ПК распаковать и запустить `deploy.bat` (нужен
  Docker Desktop и интернет для скачивания базовых образов/зависимостей при
  первой сборке).
- **Офлайн, без интернета/Maven/npm на целевом ПК** — сначала `build_and_export.bat`
  на этой машине (экспортирует готовые Docker-образы в `dist_export/`), затем
  перенести папку `dist_export/` и следовать `README-DEPLOY-OFFLINE.md`. Экспорт
  нужно повторять после значимых изменений кода — образы в `dist_export/` не
  обновляются автоматически.

## Требования к скриптам (для авторов новых задач)

Скрипт должен принимать входные параметры как **позиционные аргументы командной
строки** (в порядке, заданном в `parametersConfig` при регистрации скрипта), а
не через интерактивный ввод (`Read-Host` в PowerShell, `input()` в Python и
подобное) — панель запускает скрипт неинтерактивно. Результат нужно сохранять в
текущую рабочую директорию (`(Get-Location).Path` в PowerShell / `os.getcwd()`
в Python) — панель сама подставляет под каждый запуск отдельную папку результатов.
Если параметр допускает несколько значений через запятую (например, счета или
ЭЦП) — на каждое значение нужно создавать отдельный файл результата, панель сама
упакует их в zip при скачивании, если файлов больше одного.

Примеры адаптированных скриптов:
`backend/src/main/resources/sample-scripts/gro/gro_СБЕР.ps1` (PowerShell, счета
через запятую → отдельный JSON на счёт) и
`backend/src/main/resources/sample-scripts/ecp/generation_ECP_RaiffeisenBankApi.py`
(Python, три синхронных списка через запятую → отдельный JSON на каждую тройку).
