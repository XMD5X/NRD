# Подключение проекта к корпоративному GitLab

Как проект живёт в двух репозиториях, что нужно настроить один раз и что запускать при каждом изменении.

## Как устроено

Разработка ведётся во внешнем репозитории **GitHub** (`XMD5X/NRD`, ветка `main`). Корпоративный **GitLab** (`gitlab.dev002.local/Smolinag/nrd-business-panel`) — целевой проект: через него идут проверки качества, сборка образа и развёртывание в Kubernetes. Содержимое переносится из GitHub в GitLab вручную запускаемым job'ом зеркалирования, а не наоборот.

```
GitHub (разработка)  --[Mirror GitHub -> GitLab]-->  GitLab  --[Build]-->  registry  --[Deploy]-->  Kubernetes
```

Пайплайн лежит в самом целевом проекте — файл `.gitlab-ci.yml` в корне репозитория GitLab. Эталонная версия с комментариями: `Claude outputs/gitlab-ci-1.yml` в этом репозитории.

## Что настроить один раз

**Доступ.** Пользователь, запускающий job'ы, должен иметь роль не ниже Developer с правом push в ветку. Если ветка защищена (Settings → Repository → Protected branches), в «Allowed to push» должна быть его роль — иначе зеркалирование упадёт с 403 или 412.

**Переменные CI/CD** (Settings → CI/CD → Variables, обе — Protected + Masked):

| Переменная | Что в ней | Как получить |
|---|---|---|
| `DOCKER_AUTH_CONFIG` | `config.json` с доступом на push в registry | `{"auths":{"repo.dev002.local":{"auth":"<base64(user:password)>"}}}` |
| `KUBE_CONFIG_B64` | kubeconfig целевого кластера в base64 | `cat ~/.kube/config \| base64 -w0` |

Обе ещё не заведены — это и есть то, что блокирует автоматический деплой. Отдельный `CI_JOB_TOKEN` настраивать не нужно: пайплайн живёт в том же проекте, куда пушит, и прав токена хватает.

**Секрет приложения.** `adminpanel-secrets` (пароль БД и JWT-секрет) создаётся в кластере один раз вручную, пайплайн его не трогает — см. `k8s/helm/nrd-business-panel/README.md`, раздел «Секреты».

**Сетевые ограничения.** Раннер ходит во внешний интернет через прокси `http://s001as-c-squid.dev002.local:3128` — он уже прописан в переменной `PROXY` и нужен job'у зеркалирования, чтобы достучаться до github.com. Если с раннера недоступны `gcr.io` (образ kaniko) и Docker Hub (образ helm), зазеркальте эти образы во внутренний registry и поправьте `image:` у соответствующих job'ов.

## Что запускать при изменениях

Все три job'а — ручные (`when: manual`), запускаются кнопкой в Pipelines → Run. Порядок именно такой:

**1. `Mirror GitHub -> GitLab`** — переносит текущее состояние GitHub поверх проекта GitLab.

Две вещи, которые важно понимать до нажатия кнопки. Во-первых, `git push --mirror` удаляет в GitLab все ветки и теги, которых нет в GitHub, — локальные feature-ветки, заведённые только в GitLab, будут стёрты. Во-вторых, самого `.gitlab-ci.yml` в GitHub нет, поэтому зеркалирование его тоже стирает: job сохраняет файл до push и возвращает отдельным коммитом сразу после. Если менять этот механизм — учитывайте, что без него следующий запуск пайплайна будет неоткуда взять.

Для регулярной синхронизации без ручных нажатий можно завести Pipeline Schedule (CI/CD → Schedules) на этот же пайплайн.

**2. `Build backend image`** — собирает образ через kaniko и пушит в registry с тегами `<short-sha>` и `latest`.

Образ **один**: после отказа от nginx отдельного образа со статикой нет, фронтенд копируется внутрь образа backend. Поэтому контекст сборки — **корень репозитория**, а не каталог `backend`. Именованные контексты сборки (`--build-context`) использовать нельзя: их понимает только BuildKit, а kaniko работает с одним контекстом.

Перед сборкой в репозитории должен лежать уже собранный фронтенд — `frontend/dist-prebuilt`. CI его не собирает: `vite build` внутри контейнера на этом проекте нестабилен (см. README в корне). Собирается он на машине разработчика командой `npm ci && npm run build` в каталоге `frontend/`, результат копируется в `dist-prebuilt/` и коммитится.

Сборка идёт через kaniko, а не Docker-in-Docker, потому что kaniko не требует privileged-раннера и доступа к `docker.sock` — это обычно проще согласовать с ИБ.

**3. `Deploy (helm upgrade)`** — разворачивает чарт `k8s/helm/nrd-business-panel` в namespace `nrd-business-panel`, подставляя тег только что собранного образа.

Домен (`ingress.host`), storage class и включение NetworkPolicy берутся из `values.yaml` чарта — переопределяйте через `--set` в job'е, если отличаются от значений по умолчанию.

## Если что-то пошло не так

| Симптом | Причина |
|---|---|
| `job's stage does not exist` | Названия стадий (`build`, `deploy`) не совпадают с теми, что задаёт общий шаблон `devops/svd/ci-templates` — поправьте под реальные имена |
| Зеркалирование падает с 403 или 412 | Не хватает прав на push в защищённую ветку |
| `.gitlab-ci.yml` пропал после зеркалирования | Не отработал шаг восстановления файла — верните его коммитом вручную |
| kaniko не стартует | Недоступен `gcr.io` — зазеркальте образ executor во внутренний registry |
| Образ собрался, но под не поднимается | Проверьте, что `frontend/dist-prebuilt` закоммичен: без него приложение стартует как чистое API, без интерфейса |
| Под не проходит проверки готовности | В зависимостях нет `spring-boot-starter-actuator`, а пробы в манифестах обращаются к `/actuator/health` — известная задача, см. роадмап |

## Текущий статус

Репозиторий переведён под корпоративную систему управления доступом, пайплайн подключён к общему CI-шаблону организации и проходит проверку SonarQube. Сборка образа и деплой написаны и проверяются вручную по кнопке. Автоматический деплой не работает до появления двух CI-переменных (`DOCKER_AUTH_CONFIG`, `KUBE_CONFIG_B64`) и самого dev-кластера — merge request на его создание подан и ожидает инфраструктурную команду.
