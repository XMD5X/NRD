## 1. Что сделано

### 1.1 Приложение — функциональность

- Веб-панель (Spring Boot + React) для функциональных администраторов —
  управление и запуск скриптов (PowerShell/Python) по типовым задачам,
  включая выдачу прав доступа на счета для эталонных ролей.
- Аутентификация JWT, ролевая модель с ролью «подтверждающий изменения» для
  согласования критичных операций перед применением.
- История действий и история входов (audit trail), выгрузка в формате CEF
  (ArcSight) для интеграции с SIEM — с читаемой датой/временем в поле `rt=`.
- Мониторинг системных ресурсов backend/frontend (CPU, RAM, диск, размер БД,
  размер статики) с автообновлением раз в 10 секунд без ручной кнопки.
- Индикация пользователей онлайн в разделе пользователей.
- Выгрузка логов: backend, frontend, CEF — по кнопке на `/admin/settings`,
  с единообразным именованием файлов
  (дата + тип, без искажения кодировки при скачивании).
- Редактирование содержимого скриптов прямо в браузере (`/admin/scripts`) —
  без пересборки и повторной загрузки файла, с автоматической резервной
  копией (`.bak`) предыдущей версии.
- Security-hardening: JWT-секрет и пароль БД — только через переменные
  окружения/секреты, не в коде и не в git-истории; backend-контейнер
  работает от непривилегированного пользователя; rate limiting на
  `/api/auth/login`; security-заголовки (CSP, X-Frame-Options,
  Referrer-Policy и др.) отдаёт само приложение.

### 1.1.1 Отказ от nginx

Перед приложением больше не стоит отдельный веб-сервер. Раньше nginx раздавал
статику фронтенда, проксировал `/api` на backend, терминировал TLS,
ограничивал частоту попыток входа и писал access-логи — теперь всё это либо
делает само приложение, либо решается уровнем выше:

- статику и маршруты SPA отдаёт backend (`WebConfig`), фронтенд и API живут
  на одном порту — проксирование и CORS между ними больше не нужны;
- security-заголовки (CSP и остальные) проставляет `SecurityHeadersFilter`;
- ограничение частоты попыток входа — `LoginRateLimitFilter`; в отличие от
  nginx он отвечает обычной JSON-ошибкой, поэтому пользователь видит, что
  произошло, а не общее «Ошибка входа»;
- TLS терминируется на Ingress в Kubernetes или на балансировщике контура;
- выгрузка access-логов nginx из интерфейса убрана, вместе с требованием к
  кластеру иметь ReadWriteMany storage class (он нужен был только под общий
  том логов между backend и web).

Практический итог: вместо трёх контейнеров в стенде два, на один Dockerfile и
один конфиг меньше, в Kubernetes — минус Deployment, Service, ConfigMap и PVC.

### 1.2 Git-репозиторий, доступ и владение проектом

### 1.3 CI/CD

Инструкция по подключению и запуску — `docs/GITLAB.md`.

- Пайплайн зеркалирования: автоматический перенос содержимого внешнего
  GitHub-репозитория в корпоративный GitLab (`git clone --mirror` +
  `git push --mirror`), с защитой собственного `.gitlab-ci.yml` от
  затирания при каждой синхронизации (сохраняется до mirror-push и
  возвращается отдельным коммитом сразу после).
- Пайплайн подключён к общему организационному CI-шаблону
  (`devops/svd/ci-templates/full_ci.yml`) — сборка проходит через
  корпоративный SonarQube-чек наравне с другими проектами организации.
- Настроена доставка собранной версии до тестового контура.
- В пайплайн добавлены job'ы сборки Docker-образа backend (после отказа от
  nginx образ один: фронтенд копируется внутрь него)
  (через kaniko, без privileged-раннера) и деплоя в Kubernetes через
  `helm upgrade` — пока запускаются вручную по кнопке, не автоматически.

### 1.4 Перевод под Kubernetes

- Подготовлен полный комплект манифестов, переносящий текущий
  docker-compose-стенд (postgres, backend) в Kubernetes:
  Namespace, Secret, ConfigMap, StatefulSet (postgres), Deployment
  (backend), PVC, Ingress.
- Манифесты доведены до Helm-чарта («полный» вариант): версионируемые
  релизы (`helm upgrade`/`rollback`), все параметры (registry, домен,
  storage class, размеры ресурсов) вынесены в `values.yaml`, добавлены
  HorizontalPodAutoscaler (для web), PodDisruptionBudget, NetworkPolicy
  между всеми тремя компонентами (postgres ← backend ← web ← Ingress) и
  security-контексты контейнеров (запрет повышения привилегий, сброс всех
  linux capabilities, seccomp-профиль по умолчанию).
- Задокументированы и осознанно оставлены как есть архитектурные
  ограничения, которые требуют доработки уже на уровне кода приложения, а
  не инфраструктуры (см. раздел 3).
- Подан merge request на создание Kubernetes-кластера в dev-контуре —
  ожидает согласования инфраструктурной командой.
- Текущий стенд (до перехода на kubernetes-кластер) развёрнут в
  корпоративной среде на dev-контуре.

## 3. Что осталось сделать

### 3.1 Kubernetes — после получения кластера

Планируемая последовательность шагов:

1. **Установить приложение в dev-кластере** (`helm install`) сразу после
   его создания — развернуть Helm-чарт, завести секреты (пароль БД, JWT),
   настроить реальные значения `values.yaml` под конкретный кластер.
2. Настроить постоянный TLS-сертификат на Ingress через cert-manager или
   корпоративный CA (сейчас в манифестах — заглушка под самоподписанный
   сертификат для теста).
3. **Настроить git (CI/CD-пайплайн в GitLab) на работу с k8s-кластером**
   после развёртывания стенда — донастроить доступ CI к кластеру и
   registry (сейчас нужны CI/CD-переменные `KUBE_CONFIG_B64` и
   `DOCKER_AUTH_CONFIG`, ещё не заведены), чтобы job'ы `Build backend
   image` / `Deploy (helm upgrade)` из
   `.gitlab-ci.yml` вообще могли достучаться до dev-кластера.
4. **Провести тестовый прогон пайплайна на развёртывание в dev-контуре** —
   запустить job `Deploy (helm upgrade)` из GitLab CI (не просто `helm
   install` руками, как в шаге 1) и убедиться, что автоматический деплой
   через git в кластер реально работает end-to-end, прежде чем полагаться
   на него дальше.
6. **Проверить работоспособность приложения в dev-кластере** — убедиться,
   что стенд в Kubernetes работает так же, как текущий docker-compose
   стенд (функциональность, логи, доступность).
7. **Если проверка прошла успешно — оформить ЗнИ** на выделение
   вычислительных мощностей и сетевых связностей для test- и prod-
   контуров Kubernetes (по аналогии с dev, но под нагрузку и доступы
   тестового/промышленного контуров). До успешной проверки в dev ЗнИ на
   test/prod не подаём — сначала подтверждаем, что решение в принципе
   работает в kubernetes-окружении.
8. **После выделения мощностей под test/prod — переписать CI/CD-пайплайн
   под автоматическое развёртывание в Kubernetes.** Сейчас job'ы сборки
   образов и `helm upgrade` в `.gitlab-ci.yml` запускаются вручную
   (`when: manual`) — это осознанно для первого, ручного разворачивания в
   dev. Для test/prod ручной запуск не годится как постоянный процесс:
   нужно перевести деплой на автозапуск (по тегам/веткам или по мержу в
   `main`), с раздельными job'ами/веткой конфигурации под каждый контур
   (dev/test/prod — разные `values-<contour>.yaml`, разные namespace,
   разные CI/CD-переменные доступа к кластеру).

## 4. Риски и открытые вопросы

- Сроки перехода в Kubernetes зависят от согласования и фактического
  создания кластера инфраструктурной командой — не в зоне контроля
  проектной команды.
- Наличие подходящего ReadWriteMany storage class в целевом кластере пока
  не подтверждено — от этого зависит доступность части функциональности
  выгрузки логов в k8s-варианте развёртывания.
