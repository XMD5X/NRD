# Backend — описание

Стек: Java 21, Spring Boot 3.3, Spring Security, Spring Data JPA, Flyway, PostgreSQL,
JWT (jjwt). Сборка — Maven (`backend/pom.xml`), в проде — внутри многоэтапного
Docker-билда (`backend/Dockerfile`), образ на выходе также включает Python 3, bash
и PowerShell Core (`pwsh`) для выполнения реальных скриптов поддержки.

## Структура пакетов

```
ru.support.adminpanel
├── config          AppProperties, SecurityConfig, CorsConfig
├── security         JwtService, JwtAuthFilter, CurrentUser(Util)
├── entity           JPA-сущности (User, ScriptEntity, ScriptExecution, ...)
├── repository       Spring Data JPA репозитории
├── dto              Request/Response объекты для REST API
├── service           Бизнес-логика (в т.ч. DataSeeder — начальные данные)
├── controller       REST-контроллеры
└── exception         GlobalExceptionHandler
```

## Аутентификация и авторизация

- MVP использует собственную аутентификацию по логину/паролю (`AuthService`),
  пароли хранятся как bcrypt-хеш (`SecurityConfig.passwordEncoder`).
- При успешном входе выдаётся JWT (`JwtService`), содержащий логин, роль и id
  пользователя. Токен передаётся клиентом в заголовке `Authorization: Bearer <token>`.
- `JwtAuthFilter` на каждый запрос проверяет токен и кладёт `CurrentUser` в
  Spring Security контекст; при отсутствующем/невалидном/просроченном токене
  просто очищает контекст (запрос идёт дальше неаутентифицированным).
- `SecurityConfig` явно настраивает `authenticationEntryPoint`, который отвечает
  **401** с телом `{"error": "..."}"` на любой запрос без валидной аутентификации
  к защищённому эндпоинту. Это важно: без явного entry point Spring Security по
  умолчанию отвечает 403, а фронтенд (`api/client.js`) перехватывает именно 401,
  чтобы разлогинить пользователя и перекинуть на `/login` — без этой настройки
  страница с истёкшей сессией зависала на "Загрузка..." (реальный баг, найден и
  исправлен уже после первого деплоя).
- Проверка прав по ролям — в `SecurityConfig.filterChain` (например, `/api/users/**`
  доступен только роли `ADMIN`) и точечно в сервисах: `ExecutionController.checkSendAccess`
  — только владелец выполнения или администратор может нажать "Отправить". Просмотр
  и скачивание результатов (`GET /api/executions`, `GET /api/executions/{id}/download`)
  открыты **любому авторизованному пользователю**, а не только владельцу/админу —
  это осознанное решение: панель общая для команды поддержки, сотрудники должны
  видеть и скачивать файлы друг друга из общей истории.
- Это временное решение на период отладки; переход на AD — вне MVP (см. HLD.md, раздел 8).

## Основные сущности и их роль

| Сущность | Назначение |
|---|---|
| `User` | Пользователь, роль, статус блокировки |
| `LoginHistory` | Журнал попыток входа (успех/неудача, IP) |
| `ScriptEntity` | Зарегистрированный скрипт: путь к файлу, тип, конфигурация параметров, `category`/`bankName` для группировки на UI |
| `ScriptExecution` | Один запуск скрипта: параметры, статус, путь к результату (файл или папка с несколькими файлами), stdout/stderr |
| `UploadedFile` | Файл, загруженный бизнес-пользователем (сертификат/счёт/полномочия) |
| `ActionHistory` | Общий аудит действий (создание пользователя, блокировка, запуск скрипта и т.д.) |
| `SystemSetting` | Ключ-значение, используется для уровня логирования фронтенда |

## Выполнение скриптов (`ScriptExecutionEngine`, `ExecutionService`)

1. `POST /api/scripts/{id}/execute` — `ExecutionService.execute()` берёт
   `parametersConfig` скрипта (JSON-массив `{name, label, type}`), упорядочивает
   переданные пользователем значения по этому списку и запускает скрипт как
   локальный процесс (`ProcessBuilder`) через `ScriptExecutionEngine`:
   - `BASH` → `bash <file> <args...>`
   - `PYTHON` → `python3 <file> <args...>`
   - `POWERSHELL` → `pwsh -File <file> <args...>` (на целевом Windows Server —
     штатный `powershell.exe`, см. HLD раздел 7)
2. Рабочая директория для каждого запуска — отдельная папка
   `data/results/<execution_id>` — туда скрипт должен класть файлы результата.
   **Скрипт может создать несколько файлов** (по одному на каждое значение из
   параметра со списком через запятую — например, на каждый счёт или каждую
   ЭЦП): `ScriptExecution.resultFilePath` в этом случае хранит путь к **папке**,
   а не к одному файлу. `ExecutionService.listResultFiles()` перечисляет все
   файлы внутри (с обратной совместимостью для старых записей, где путь вёл
   сразу на файл).
3. Результат (stdout/stderr, статус `GENERATED`/`FAILED`) сохраняется в
   `ScriptExecution` и виден пользователю в UI.
4. Скачивание (`GET /api/executions/{id}/download`) отдаёт файл напрямую, если
   он один, либо упаковывает все файлы в zip на лету (`ExecutionService.zipResultFiles`,
   `java.util.zip.ZipOutputStream`), если их несколько — тогда же
   `Content-Disposition` содержит имя `execution_<id>_results.zip`.
5. `GET /api/executions` (`ExecutionController.all()`) — общая история всех
   выполнений всех пользователей (для страницы "История"), обогащённая именем
   скрипта/категорией/банком и логином автора через batch-джойн
   (`allExecutionsWithDetails()`), без N+1-запросов.
6. `POST /api/executions/{id}/send` — отдельный шаг "Отправить" (доступен только
   владельцу выполнения или администратору, см. выше). Если у скрипта задан
   `sendScriptPath` (отдельный скрипт-отправитель) — он запускается с путём к
   результату в качестве аргумента. Если не задан — считается, что отправка
   (включая авторизацию) уже реализована внутри самого генерирующего скрипта
   (как в реальном примере заказчика), и шаг лишь фиксирует факт отправки в аудите.

### Требования к скриптам

Скрипт **обязан** принимать параметры как позиционные CLI-аргументы, а не через
интерактивный ввод (`Read-Host` в PowerShell, `input()` в Python и подобное) —
панель запускает скрипт неинтерактивно и не отвечает на приглашения ввода.
Путь сохранения результата — текущая рабочая директория, которую панель
подставляет под каждый запуск (`(Get-Location).Path` / `os.getcwd()`).

Если один из параметров допускает несколько значений через запятую (счета,
ЭЦП и т.п.) — скрипт должен в цикле создавать **отдельный файл на каждое
значение**; панель сама обнаружит несколько файлов в папке результата и
предложит скачивание zip-архивом. Примеры:

- `backend/src/main/resources/sample-scripts/gro/gro_СБЕР.ps1` — PowerShell,
  параметры `userId` + `accounts` (через запятую), `foreach ($account in
  $accounts.Split(','))` → JSON на каждый счёт. По этому шаблону адаптированы
  все банковские PS1-скрипты (папки `gro/`, `gup/`, `vk_rub/`, `vk_valuta/`,
  `sap_pi/`, `prosmotr_vlozheniy/`).
- `backend/src/main/resources/sample-scripts/ecp/generation_ECP_RaiffeisenBankApi.py` —
  Python, три параметра через запятую (`comments`, `numbers_ecp`, `exp_dates_ecp`),
  синхронизированные по индексу — JSON на каждую тройку (= каждую ЭЦП).

Таймаут выполнения одного скрипта — 120 секунд (`ScriptExecutionEngine`), при
превышении процесс принудительно завершается, выполнение помечается ошибкой.

## Категории и группировка задач (`category`, `bankName`)

`ScriptEntity` содержит необязательные поля `category` и `bankName`
(миграция `V3__scripts_category.sql`). `DataSeeder` заполняет их для всех
реальных скриптов поддержки (например, `category = "ГРО (Платежи в рублях)"`,
`bankName = "СБЕР"`), чтобы фронтенд мог сгруппировать задачи в дерево
"категория → банк"/отдельные плашки без хардкода на бэкенде — см. `docs/FRONTEND.md`.
`DataSeeder` идемпотентен (`existsByName` перед вставкой), поэтому повторные
деплои не создают дублей при добавлении новых категорий/банков.

## Файловое логирование фронтенда

- `POST /api/logs` (`LogController` → `FrontendLogService`) принимает батч
  записей от фронтенда и дописывает их в файл `data/logs/frontend/frontend-YYYY-MM-DD.log`.
- Уровень логирования на клиенте регулируется через `GET/PUT /api/system/log-level`
  (`SystemController` → `SystemSettingService`, хранится в таблице `system_settings`).
- `LogRotationScheduler` ежедневно в 03:00 архивирует файлы логов старше 7 дней
  (`app.frontend-log-retention-days`) в zip и удаляет исходный файл
  (`FrontendLogService.rotateAndArchive`).

## REST API

Полная таблица эндпоинтов — в `HLD.md`, раздел 5 (обновлена с учётом истории
выполнений и текущей модели прав). Формат ошибок — единый JSON
`{"error": "текст"}` (см. `GlobalExceptionHandler`), включая ответ 401 от
`authenticationEntryPoint`.

## Конфигурация

Все параметры вынесены в переменные окружения (см. `application.yml` и
`docker-compose.yml`): строка подключения к БД, секрет JWT, каталоги для файлов,
срок хранения логов. Значения по умолчанию рассчитаны на локальный запуск.

## Демо-данные и реальные скрипты (`DataSeeder`)

При первом запуске (`DataSeeder`) создаются: пользователь `admin` (роль ADMIN),
пользователь `business` (роль BUSINESS_USER), демонстрационный Python-скрипт
"Проверка статуса пользователя", а также **все реальные адаптированные скрипты
поддержки** — 6 категорий × до 7 банков ("Выдача прав доступа...") плюс отдельная
задача "Генерация ЭЦП". Старые демо-записи ("Генерация запроса на полномочия по
счетам" и промежуточный формат имени без категории) деактивируются
(`deprecateOldPermissionsDemo`), чтобы не плодить дубли при повторных деплоях на
одной и той же БД.

## Ограничение среды подготовки MVP

Код изначально готовился без возможности скомпилировать backend через Maven в
изолированной среде — это ограничение снято: backend собирается и работает на
целевой машине через Docker (`backend/Dockerfile`, многоэтапная сборка Maven
внутри контейнера). У frontend, наоборот, сборка **внутри Docker на этой машине**
не работает (см. `README.md`) — этим и объясняется, почему `frontend/Dockerfile`
не собирает `vite build` сам, а раздаёт заранее подготовленную статику.
