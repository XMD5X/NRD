# Описание ИТ-решения: Админ-панель поддержки

## Назначение

Система заменяет ручной запуск скриптов поддержки через RDP/SSH на веб-интерфейс
с ролевым доступом, аудитом и возможностью самообслуживания для бизнес-заказчиков
(загрузка сертификатов, счетов, настройка полномочий без обращения в ИТ). Полное
бизнес-обоснование — в `REFINED_VISION.md`.

## Архитектура на верхнем уровне

Система состоит из трёх основных слоёв, разворачиваемых на одном сервере (MVP,
масштаб — до 10 пользователей, до 10 запусков в день):

1. **Frontend** — одностраничное веб-приложение (React), обращается к backend
   исключительно через REST API (`/api/*`).
2. **Backend** — Java/Spring Boot приложение: аутентификация, ролевая модель,
   запуск скриптов, хранение аудита, приём файловых логов фронтенда.
2. **База данных** — PostgreSQL: пользователи, история авторизаций и действий,
   метаданные скриптов и выполнений, метаданные загруженных файлов.

Nginx стоит перед всем стеком: раздаёт статику React и проксирует `/api` на
backend. Подробная архитектура, диаграммы компонентов и данных — в `HLD.md`.

## Ключевые технические решения

| Область | Решение | Причина |
|---|---|---|
| Аутентификация (MVP) | Логин/пароль в собственной БД (bcrypt) | Временное решение на период отладки; далее — переход на AD (вне MVP) |
| Роли | ADMIN, BUSINESS_USER, назначаются вручную в БД | AD-группы — вне MVP |
| Выполнение скриптов | Локальный процесс на машине backend (`ProcessBuilder`) | Скрипты и панель работают на одной машине (решение из SA-интервью) |
| Отправка в целевую систему | Логика внутри самого скрипта, панель только запускает | Заказчик подтвердил: авторизация/отправка уже реализованы в скриптах |
| Хранение файлов | Диск + метаданные в БД | Не раздувает БД, стандартный подход |
| Логирование фронтенда | Файлы на сервере, 4 уровня (INFO/DEBUG/WARNING/TRACE), ротация 7 дней + архив | Требование из технического задания |

## Что не входит в MVP

- Интеграция с Active Directory (доменная авторизация, группы доступа).
- Автоматическая блокировка при подборе пароля.
- Самообслуживание администратора по настройке полей форм скриптов через UI.
- CI/CD, мониторинг/алертинг, резервное копирование БД и файлов.

Подробный список рисков и допущений — раздел 9 `HLD.md`.

## Текущий статус (актуализировано)

Стенд собран и работает на выделенной Windows-машине через **Docker Compose**
(не Windows Service, как изначально предполагалось в HLD — см. `docs/HLD.md`,
раздел 0). Панель доступна на `http://localhost:18080`. В систему загружены и
проверены реальные скрипты поддержки по 6 категориям эталонных ролей (ГРО, ГУП,
Права просмотра, Валютный контроль Рубли/Валюта, SAP-PI) × до 7 банков, плюс
отдельная задача "Генерация ЭЦП" (Python, регистрация сертификатов для
RaiffeisenBankApi). Добавлены страница общей истории выполнений (кто/когда/что
сгенерировал, скачивание в т.ч. zip-архивом при нескольких файлах результата) и
фирменное оформление СИБУР.

## Как передать проект команде / развернуть на другой машине

1. Распаковать архив, ознакомиться с `README.md` (инструкции по запуску,
   особенность сборки frontend на этой машине).
2. На машине с обычным доступом в интернет (Maven Central, Docker Hub) убедиться,
   что Docker Desktop запущен, и запустить `deploy.bat` (или `docker compose up
   --build -d`).
3. Проверить базовый сценарий: вход под `admin`/`admin12345`, запуск любого
   реального скрипта поддержки (например, категория "ГРО (Платежи в рублях)" →
   банк), скачивание результата, страница "История".
4. Для офлайн-переноса без интернета/Maven/npm на целевой машине — см.
   `README-DEPLOY-OFFLINE.md` (`build_and_export.bat` экспортирует готовые
   Docker-образы).
5. Далее — планирование следующих итераций согласно разделу 10 `HLD.md` (переход
   на AD, мониторинг, резервное копирование).
