# Frontend — описание

Стек: React 18, React Router 6, Axios, сборка через Vite. Без сторонней UI-библиотеки
(стили в `src/styles.css`, включая фирменную палитру СИБУР — см. раздел "Брендинг"
ниже) — осознанно минимальный набор зависимостей для MVP.

**Особенность сборки на этой машине:** `vite build` внутри Docker стабильно падает
(esbuild/vite конфликт, похоже на локальную особенность окружения) — поэтому
frontend собирается вручную (`npm ci && npm run build`) и готовая статика кладётся
в `frontend/dist-prebuilt/`, откуда её просто раздаёт nginx в Docker-сборке. См.
`README.md`, раздел "Особенность сборки frontend на этой машине" — это нужно
повторять после каждого изменения в `frontend/src/`.

## Структура

```
frontend/src
├── main.jsx              точка входа, роутер, AuthProvider
├── App.jsx                маршруты приложения
├── styles.css              стили + CSS-переменные фирменных цветов СИБУР
├── api/client.js           axios-клиент с перехватчиками (JWT, 401 → редирект на /login)
├── context/AuthContext.jsx  состояние аутентификации (токен, роль, логин)
├── components/
│   ├── Layout.jsx           общий каркас (шапка с лого СИБУР, навигация по ролям)
│   ├── SiburLogo.jsx         SVG-лого (оригинальный знак, не копия официального логотипа)
│   └── ProtectedRoute.jsx   защита маршрутов (авторизован / только админ)
├── pages/
│   ├── LoginPage.jsx         вход (с лого и фирменным цветом)
│   ├── DashboardPage.jsx      список задач: плашки категорий + общая карточка "эталонных ролей"
│   ├── ExecutionPanel.jsx     форма параметров, запуск, статус, скачивание (в т.ч. zip), отправка
│   ├── HistoryPage.jsx        история всех выполнений всех пользователей, скачивание результатов
│   ├── UploadPage.jsx         загрузка сертификатов/счетов/полномочий (US-4)
│   ├── AdminUsersPage.jsx     управление пользователями, блокировка, история
│   ├── AdminScriptsPage.jsx   добавление и включение/отключение скриптов
│   └── AdminSettingsPage.jsx  переключение уровня логирования фронтенда
└── logging/logger.js         файловое логирование (см. ниже)
```

## Маршруты и роли

| Маршрут | Доступ | Страница |
|---|---|---|
| `/login` | Все | Вход |
| `/` | Авторизован | Список задач и запуск |
| `/history` | Авторизован | История всех выполнений (общая для команды) |
| `/uploads` | Авторизован | Загрузка файлов |
| `/admin/users` | ADMIN | Пользователи, блокировка, история |
| `/admin/scripts` | ADMIN | Управление скриптами |
| `/admin/settings` | ADMIN | Уровень логирования |

`ProtectedRoute` перенаправляет неавторизованных на `/login`, а обычных
пользователей — с админских разделов на главную.

## Список задач (`DashboardPage.jsx`) — плашки категорий

Скрипты приходят с backend с полями `category`/`bankName` (см. `docs/BACKEND.md`).
Фронтенд группирует их на две зоны:

1. **Общая карточка «Выдача прав доступа на счета для эталонных ролей»** — только
   для фиксированного набора категорий из константы `ACCESS_RIGHTS_CATEGORIES`
   (ГРО, ГУП, Права просмотра, Валютный контроль Рубли/Валюта, SAP-PI). Внутри —
   двухуровневый селектор "эталонная роль → банк".
2. **Отдельные плашки** — любая категория **вне** этого списка (сейчас это
   «Генерация ЭЦП») получает свою собственную карточку с заголовком-категорией;
   если в категории только один "банк/модуль" — селектор банка не показывается
   (выбирается автоматически через `useEffect`, чтобы не показывать
   бесполезный select из одного пункта).

Это сделано намеренно расширяемо: чтобы добавить новую категорию как отдельную
плашку, на фронтенде **ничего менять не нужно** — достаточно завести её в
`DataSeeder` под именем, которого нет в `ACCESS_RIGHTS_CATEGORIES`.

Загрузка списка задач обёрнута в `.catch()/.finally()` (не только `.then()`) —
иначе при любой ошибке запроса (истёкшая сессия, сеть, 5xx) `loading` навсегда
оставался бы `true`, и страница висела на "Загрузка..." — это реальный баг,
найденный и исправленный (см. также `docs/BACKEND.md`, про 401 вместо 403).

## Работа со скриптами (динамические формы)

`ScriptEntity.parametersConfig` — JSON-массив вида
`[{"name":"userId","label":"User ID","type":"text"}]`, который приходит с backend
в `ScriptResponse.parametersConfig`. `ExecutionPanel.jsx` парсит его и рендерит
поля формы динамически — то есть при добавлении нового скрипта с новым набором
параметров разработчику не нужно менять frontend, если тип поля — простой текст.
Это в равной мере работает и для параметров "счета через запятую", и для трёх
синхронных списков ЭЦП-скрипта — каждый параметр это просто ещё одно текстовое
поле формы. (Настройка `parametersConfig` — задача разработчика при регистрации
скрипта, не самообслуживание администратора, см. HLD.md, границы MVP.)

## Скачивание результата (в т.ч. zip)

`ExecutionPanel.jsx` и `HistoryPage.jsx` скачивают файл авторизованным
`GET`-запросом с `responseType: 'blob'` (прямая ссылка не подойдёт — JWT передаётся
заголовком, а не cookie) и триггерят сохранение через временный `<a download>`.
Кнопка скачивания показывает `Скачать (N, zip)`, если `resultFileCount > 1` —
backend в этом случае уже отдаёт готовый zip-архив (см. `docs/BACKEND.md`).

## Брендинг СИБУР

`src/styles.css` — CSS-переменные фирменных цветов (`--sibur-teal` — официальный
зелёный `#55b4c7`; тёмно-зелёный/мятный/оранжевый — по актуальному описанию
палитры бренда, точные HEX которых не публикуются в открытом брендбуке).
`components/SiburLogo.jsx` — простой оригинальный SVG-знак (не копия официального
логотипа СИБУР, который защищён и не подлежит видоизменению) в фирменных цветах,
используется в шапке (`Layout.jsx`) и на странице входа (`LoginPage.jsx`).

## Файловое логирование (`src/logging/logger.js`)

- Поддерживает уровни `TRACE < DEBUG < INFO < WARNING`, по умолчанию `INFO`.
- Уровень читается/устанавливается через `/api/system/log-level`
  (`AdminSettingsPage.jsx`) и применяется в текущей сессии клиента.
- Вызовы `logger.info/debug/warning/trace(message, context)` расставлены в
  ключевых местах (вход, запуск скрипта, загрузка файлов, действия администратора).
- Записи буферизуются и раз в 3 секунды батчем отправляются на `POST /api/logs`;
  при закрытии вкладки — досылаются через `navigator.sendBeacon`.
- Backend дописывает их в файл на диске с ротацией (см. `BACKEND.md`).

## Аутентификация на клиенте

JWT-токен и данные пользователя (роль, логин) хранятся в `localStorage`
(обычное поведение SPA-приложения). `api/client.js` подставляет токен в заголовок
`Authorization` для каждого запроса и обрабатывает **401** (разлогинивает
пользователя и редиректит на `/login`) — важно, что backend теперь явно
возвращает именно 401 (а не 403 по умолчанию) на невалидный/просроченный токен,
см. `docs/BACKEND.md`.

## Dev-режим и продакшен-сборка

- Разработка: `npm run dev` (Vite dev-server, порт 5173, проксирует `/api` на
  `localhost:8080`, см. `vite.config.js`).
- Продакшен: `npm run build` → статические файлы в `dist/`, которые нужно вручную
  скопировать в `dist-prebuilt/` (см. раздел про сборку выше) — раздаются через
  nginx (`frontend/Dockerfile`, `nginx/nginx.conf`), который же проксирует
  `/api` на backend-контейнер.
